# Análisis Backend — Fiscal Agent

> **Paquete**: `fiscal_agent/` (v2.0.0) — backend del producto VerticalAI
> **Fecha**: 2026-08-10
> **Objetivo**: Reporte de arquitectura, estructura y código del backend para auditoría técnica.
> **Método**: Lectura y verificación de código fuente (repo git). No se ejecutaron tests (auditoría de solo lectura). `.env.prod` no fue inspeccionado (contiene secretos; se detalla su existencia y riesgo, nunca su contenido).

---

## 0. Resumen ejecutivo

Fiscal Agent es un backend Python que **integra el padrón y deuda de ARCA/AFIP (WS-SOAP), automatiza navegación de browser vía Composio para extraer deuda, facilidades, registro tributario e IIBB (Córdoba), genera PDFs de reportes fiscales, y expone todo por tres superficies**: API HTTP REST (FastAPI), servidor MCP (stdio/HTTP) y CLI (Typer). Usa Redis como store de tenants/API keys/conversaciones y Engram como memoria persistente por contribuyente.

**Lo que un auditor debe saber primero**:

1. El backend funciona y está en producción para clientes reales, pero **la suite de tests está desincronizada y no compila contra el código actual** (imports de enums que ya no existen).
2. **Hay un bug confirmado**: `POST /v1/chat/message` (flujo no-streaming) con intención "reporte" siempre falla con `NameError`.
3. **El transporte HTTP de MCP no tiene autenticación** (TODO explícito en el código).
4. **Hay secretos en el repo**: un CUIT por defecto hardcodeado en `config.py`, clave fiscal del estudio embebida en flujos de browser, y un `.env.prod` en la raíz.
5. IIBB para **Jujuy es un stub** que devuelve estructuras vacías en silencio; **idempotencia declarada pero no implementada**.

## 3. Punto de entrada y runtime

- `python -m fiscal_agent` → `__main__.py`: el subcomando `mcp` llama `mcp.transport.run_mcp()`; todo lo demás → `cli.main()` (Typer).
- **Orquestador compartido**: `cli._procesar_cliente_pipeline(cliente, token, sign, engine, pdf_gen, mes, anio, browser, with_deuda, with_facilidades, with_registro, with_iibb, send_email, config, memory_client, echo_func)` — usado por CLI, handlers de chat y MCP `run_pipeline`.
- **Runtime** (FastAPI): lifespan conecta Redis (`decode_responses=True`), crea `RedisStore` + `TenantStore.seed_defaults()`, cierra al shutdown.
- **Modelo de concurrencia**: todo es **request-driven**; no hay schedulers (no APScheduler/Celery/cron). El trabajo pesado síncrono (SOAP, browser, SMTP) corre en `asyncio.to_thread`.
- Middleware en orden: CORS → RateLimit → TenantContext → Auth → Metrics → Route.

| Método | Ruta | Autenticación | Propósito |
|--------|------|---------------|-----------|
| GET | `/v1/health` | Pública | Health check Redis/Engram/TA/Composio → `SystemHealth` |
| POST | `/v1/calendar` | API key | `CalendarRequest{cuit, mes, anio, idempotency_key}` |
| GET | `/v1/taxpayer/{cuit}` | API key | Constancia Padrón A5 |
| POST | `/v1/report` | API key | Pipeline completo + PDF + email |
| POST | `/v1/extract` | API key + `COMPOSIO_API_KEY` + `ESTUDIO_CLAVE_FISCAL` | Extracción browser (error `COMPOSIO_KEY_MISSING`) |
| GET/POST | `/v1/memory/{cuit}[/{obs_type}]`, `/v1/memory/observe` | API key | Historial/observaciones de memoria (contenido ≤ 10 KB) |
| CRUD | `/v1/conversations` | API key | Por tenant; camelCase `updatedAt`/`messageCount` |
| POST | `/v1/admin/register` | **Pública** | Alta de developer `{name, email}` |
| POST | `/v1/admin/apps`, `/v1/admin/apps/{id}/keys`, `/v1/admin/apikeys` | API key | Apps, claves, scopes por tenant |
| GET | `/v1/admin/tenants`, `/v1/admin/tenants/{id}`, keys, deactivate | API key | Gestión de tenants |
| GET | `/v1/system/metrics\|services\|activity\|errors` | API key | Monitoreo (cache Redis; mapa de errores timeout/arca/composio/engram/redis/validation) |
| POST | `/v1/chat/message` | API key / Clerk | NL → intent → CUIT → dispatch en thread pool |
| POST | `/v1/chat/message/stream` | API key / Clerk | SSE: `conversation_start` → `progress`* → `complete` (`pipeline_steps`) |
| POST | `/v1/chat/wizard` | API key / Clerk | Multi-turno SSE: `wizard_state` → `progress` → `complete` + `pdf_url` |
| GET | `/v1/chat/reports/{filename}` | API key | Sirve PDFs desde `/app/output` o `storage/` (controla path-traversal) |

**Modelo de autenticación** (`middleware/auth.py` + `clerk.py`):

- API keys con prefijo `fa_`; se guarda el **SHA-256** de la key (`tenant:keyhash:{sha256}`). Cadena: ApiKey → App → Developer → Plan.
- Rutas públicas: `/v1/health`, `/v1/admin/register`.
- Alternativa Clerk JWT: HS256 en dev (`CLERK_SECRET_KEY`) / RS256 en prod con JWKS cacheado en Redis (TTL 3600s).
- Rate limiting: Redis Sorted Sets, ventanas 60s + 86400s, default 10 RPM / 100 RPD, `429` con `Retry-After`.
- Métricas: middleware in-memory p50/p95/p99 por endpoint.

## 6. Integraciones externas

### ARCA/AFIP (`arca_ws.py`)
- WS-SOAP propio (cryptography + requests). `WSAA_URL=https://wsaa.afip.gov.ar/ws/services/LoginCms`; Padrón A5/A13 bajo `aws.afip.gov.ar`.
- `ARCA_PROXY_URL`: proxy HTTP-CONNECT para WSL2 (solo wsaa/aws).
- `get_ta()` con caché; `get_ta_error()` usado por chat.

### Composio Browser (`browser/composio.py`)
- REST directo: `POST https://backend.composio.dev/api/v3.1/tools/execute/{slug}` con `x-api-key`.
- Tools: `BROWSER_TOOL_CREATE_TASK`, `WATCH_TASK`, `GET_SESSION`, `STOP_TASK`. Polling 2s con reintentos ante errores transitorios.

### Workflows de browser (`browser/workflows/`)
- `login.py`: login en ARCA.
- `registro.py`: Sistema Registral → RUT.
- `full.py`: cuentas tributarias → vencimientos; taxonomía de errores ARCA-1/2/3/4/6/7.
- `iibb/cordoba.py`: DGR Córdoba `rentascordoba.gob.ar/emision/perfil/impuestos` → Pagos Mensuales → Ingresos Brutos.
- `iibb/jujuy.py`: **STUB** — devuelve JSON vacío via `done(...)`; no hay integración real (en `iibb_router.py` Jujuy está comentado: "inhabilitado hasta tener el template real").
- `factory.py`: encadena deuda → facilidades → registro → iibb.

### Memoria Engram (`memory/client.py`)
- HTTP a `MEMORY_ENGRAM_URL` (default `http://localhost:7437`), sesión por CUIT `cuit-{cuit}`.
- Cache Redis con TTLs: padrón 24 h, extracción 7 d, pipeline 1 h. **Best-effort: nunca lanza excepciones.**

### Email (`email_sender.py`)
- smtplib; puerto 465 → `SMTP_SSL`, si no STARTTLS. Aislamiento por cliente en `enviar_lote()`. Firma "Estudio Contable".

## 9. Lógica de dominio fiscal

- **Calendario**: `rules_engine.py` es un motor determinista sobre `calendario_afip.json` + `feriados.csv` (cálculo de vencimientos según tipo de contribuyente y provincia).
- **Intents de chat** (`chat/intent_router.py`): `Intent` define solo `UNKNOWN`, `TAXPAYER_QUERY`, `REPORTE_COMPLETO`. Detección por regex de CUIT + matching de palabras clave.
- **Matching IIBB Córdoba** (`memory/brain.py` `_match_rentas`): ≥2 provincias Y `idImpuesto ∈ {5904,5902,5905,5906,215}` Y el registro contiene "CORDOBA" (normalizado, sin acentos).
- **Pipeline**: `PipelineService` orquesta padrón + deuda + facilidades + registro + IIBB + PDF + email vía `_procesar_cliente_pipeline`.
- ⚠️ Bug conocido en `pdf_generator.py` `_build_detalle`: mapea `Vencimiento` → `{'Vencimiento','Importe','Concepto','Período','Obs.'}` con fuzzy token-match de importe (`DeudaDetail.saldo` → `DeudaItem.importe` legacy).
