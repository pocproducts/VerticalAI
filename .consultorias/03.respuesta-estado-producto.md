## 1. Executive TL;DR

**Fiscal-Agent es hoy una herramienta de automatización fiscal desplegable, no un producto SaaS.** Funciona en producción para un estudio contable real, automatizando consultas al Padrón A5 de ARCA vía SOAP, generación de calendarios de vencimientos, extracción de deuda vía browser automation (Composio), generación de PDFs y envío por email. Tiene 4 entry points (CLI, REST API, MCP server, 3 frontends), una arquitectura desacoplada con `PipelineService` compartido, y tests que pasan en entorno controlado. **Pero no puede venderse como SaaS hoy**: requiere que cada cliente tenga infraestructura propia (Docker Compose), certificados electrónicos de ARCA, config manual de `clients.yaml`, y acceso a Composio. No hay multi-tenancy, no hay onboarding self-service, no hay pricing, no hay monitoreo, no hay CI/CD. Es un pipeline funcional empaquetado como herramienta interna, no como producto comercializable. El camino a 1000 clientes requiere primero decidir qué modelo de negocio se construye (producto SaaS, consultora productizada, o licencia enterprise) y luego construir la plataforma que lo soporte.

## 4. Architectural Readiness — Cómo nos posicionan los refactors recientes

Los últimos 6 issues resueltos dejaron la arquitectura en un estado notablemente mejor para escalar. Esto es lo que tenemos y cómo sirve al GTM:

### 4.1 PipelineService extraído (`fiscal_agent/pipeline/service.py`)

**Qué cambió**: La lógica de pipeline vivía en `cli._procesar_cliente_pipeline()` como función embebida. Ahora es `PipelineService` con constructor injection (`RulesEngine`, `PdfGenerator`, `FiscalMemoryClient` opcional) y devuelve `PipelineResult(BaseModel)` tipado.

**Por qué importa para GTM**:
- Cualquier entry point (CLI, API, MCP) puede ejecutar el mismo pipeline con el mismo comportamiento
- Se puede testear unitariamente sin depender del CLI (inyectando mocks de `RulesEngine`, `PdfGenerator`)
- `PipelineResult` como Pydantic model permite serializar a JSON para API REST, MCP tools, o almacenamiento
- Facilita construir un **worker queue** (cada pipeline es un job ejecutable por separado)

**Archivos**: `fiscal_agent/pipeline/service.py`, `fiscal_agent/pipeline/models.py`

### 4.2 Browser Factory centralizado (`fiscal_agent/browser/factory.py`)

**Qué cambió**: `build_browser_tasks()` reemplazó la creación manual y repetitiva de `VencimientosDeudasTask`, `FacilidadesTask`, etc. en 3 lugares distintos (CLI, API, pipeline).

**Por qué importa para GTM**:
- Si necesitamos cambiar cómo se construyen las tareas de browser (ej: agregar un nuevo task, cambiar parámetros), se hace en un solo lugar
- El factory puede crecer para soportar selección de proveedor de browser (Composio vs Playwright directo vs mock para testing)
- Separa la lógica de "qué tareas correr" de "cómo se construyen"

**Archivos**: `fiscal_agent/browser/factory.py`, `fiscal_agent/browser/task.py`

### 4.3 Task System con BaseTask ABC (`fiscal_agent/tasks/base.py`)

**Qué cambió**: Se introdujo `BaseTask` como ABC con protocolo unificado. `ApiTask` (para llamadas SOAP/REST sincrónicas, como `PadronApiTask`) y `BrowserTask` (para tareas de navegación web) ahora comparten la misma interfaz.

**Por qué importa para GTM**:
- Nuevos tipos de tareas (ej: consulta SIFEN Córdoba, verificación de CUIT en ARCA vía API REST, extracción de datos de AFIP vía web scraping) se pueden agregar como subclases sin tocar el pipeline
- El sistema es extensible por diseño — se puede ofrecer un "marketplace" de tareas fiscales
- Permite separar tareas síncronas (rápidas, deterministas) de asíncronas (browser, lentas, frágiles)

**Archivos**: `fiscal_agent/tasks/base.py`, `fiscal_agent/tasks/padron.py`

### 4.4 Shared TA Cache (`fiscal_agent/arca_ws.py`)

**Qué cambió**: La función `get_ta()` ahora tiene un cache compartido (singleton con TTL) en lugar de obtener un nuevo Token de Acceso por cada consulta. CLI, API, y MCP usan la misma función.

**Por qué importa para GTM**:
- Reduce llamadas SOAP a ARCA (cada TA request genera un round-trip a ARCA y consume cuota de certificado)
- Mejora performance de pipelines con múltiples clientes (un solo TA para todos los CUITs)
- La abstracción permite migrar a un TA service centralizado (podríamos tener un servicio dedicado que emita TAs para todos los tenants)

**Archivos**: `fiscal_agent/arca_ws.py`

### 4.5 Memory Client con API pública (`fiscal_agent/memory/`)

**Qué cambió**: `FiscalMemoryClient` ahora tiene `save_observation()` y `cuit_session_id()` como métodos públicos. Se limpió la interfaz y se agregó Redis cache para evitar consultas repetidas a Engram.

**Por qué importa para GTM**:
- Trazabilidad por cliente/CUIT (saber qué pipelines se ejecutaron, qué resultados dio cada extracción)
- Base para **audit logging** (requerido si el producto maneja datos fiscales de terceros)
- Base para **cost attribution** (saber cuántas consultas SOAP, cuántas extracciones browser, cuántos PDFs por cliente)

**Archivos**: `fiscal_agent/memory/client.py`, `fiscal_agent/memory/brain.py`

### 4.6 Config constants unificadas (`fiscal_agent/config.py`)

**Qué cambió**: `CERT_PATH`, `KEY_PATH`, `REPRESENTANTE_CUIT` y otras constantes ahora viven en `config.py` y se importan desde ahí, no desde `.env` directo ni desde `cli.py`.

**Por qué importa para GTM**:
- Centralizar configuración facilita el multi-tenant (en lugar de leer `.env`, leeríamos `tenant_config[t_id]`)
- Un solo punto de cambio para paths, URLs, credenciales
- Base para un **config service** externo (AWS Parameter Store, Vault, etc.)

**Archivos**: `fiscal_agent/config.py`

## 5. Recommended Next Steps — Qué construir y en qué orden

La secuencia recomendada prioriza **validación comercial primero, escalabilidad técnica después**. La tentación de construir el SaaS multi-tenant completo antes de vender es el camino más caro y riesgoso.

### Fase 0: Inmediato (Semanas 1-4) — Preparar para vender

**Objetivo**: Poder mostrar el producto a un prospecto y cerrar los primeros 3-5 clientes como consultora productizada.

| # | Qué | Por qué | Archivos/áreas |
|---|---|---|---|
| 1 | **Demo environment** — Servidor con Docker + pipeline + datos de ejemplo para mostrar en vivo | Sin demo no hay venta. Necesitamos mostrar el pipeline corriendo en 5 minutos. | Docker Compose + script de seed con CUITs demo |
| 2 | **Landing page actualizada** con propuesta de valor clara (no técnica) | El sitio actual muestra tecnología, no valor. Debe decir: "Automatizamos la gestión fiscal de tu estudio." | `frontend/` (landing page) |
| 3 | **Deck comercial** + propuesta de implementación | Para venta founder-led. Incluir: qué incluye, qué no, timeline, pricing tentativo. | Nuevo documento comercial |
| 4 | **Lista de 50 estudios contables objetivo** para outbound | Basado en directorios de consejos profesionales. Empezar con CABA + Córdoba + Rosario. | Externa (Google Sheets, CRM) |
| 5 | **Métrica de browser automation success rate** | Entender qué tan confiable es la extracción browser antes de prometerla. Agregar logging de tasa de éxito. | `fiscal_agent/browser/task.py` |

### Fase 1: Corto plazo (Meses 1-3) — Operar los primeros clientes

**Objetivo**: Cerrar 5-10 clientes como implementaciones asistidas, aprender del feedback, refinar el producto.

| # | Qué | Por qué | Archivos/áreas |
|---|---|---|---|
| 6 | **Onboarding semi-automated** — Script que guía la configuración de certificados + `clients.yaml` | Reducir las 2-4 horas de setup a <30 minutos. | `fiscal_agent/cli.py` (nuevo comando `setup`) |
| 7 | **Dashboard de monitoreo básico** — Tablero con estado de pipelines, tasa de éxito, logs | El founder no puede ser el monitoreo. Necesitamos saber si un pipeline falló sin mirar la terminal. | `frontend/dashboard` + logging estructurado |
| 8 | **Alertas básicas** — Email/Slack cuando un pipeline falla | Escalar soporte sin estar 24/7 mirando. | Nuevo módulo de alertas + `fiscal_agent/pipeline/service.py` |
| 9 | **Kit de onboarding para clientes** — Documentación de requisitos, pasos, troubleshooting | Que el cliente pueda preparar su entorno antes de que el equipo técnico intervenga. | Nuevo `docs/` o `README-client.md` |
| 10 | **Validar pricing con clientes reales** — Entrevistas post-implementación para ajustar precios | El pricing tentativo de USD $99/mes necesita validación con pagadores reales. | Proceso de entrevistas |

### Fase 2: Mediano plazo (Meses 3-6) — Preparar escalabilidad técnica

**Objetivo**: Construir la base técnica para escalar sin multiplicar el equipo.

|---|---|---|---|

| 12 | **Multi-tenancy v1** — `tenant_id` en PipelineService, configuración por tenant, base de datos separada por tenant o tenant-scoped | El paso más grande hacia SaaS. Sin esto, cada cliente es una instancia separada. | `fiscal_agent/pipeline/`, `fiscal_agent/config.py`, nuevo módulo `tenant/` |

## Resumen de riesgo GTM

| Riesgo | Severidad | Mitigación |
|---|---|---|
| **Demanda no validada** | 🔴 Crítico | Fase 0: salir a vender con consultora productizada antes de construir más producto. Si no se venden 3-5 implementaciones en 60 días, repensar el modelo. |
| **Browser automation frágil** | 🟠 Alto | Fase 2: agregar graceful degradation, retry, alertas. En el corto plazo, no prometer extracción browser como feature core en ventas. |
| **Onboarding manual** | 🟠 Alto | Fase 1: semi-automatizar. Que un setup que hoy toma 2-4 horas baje a 30 minutos. |
| **Sin multi-tenancy** | 🟡 Medio | Fase 2: necesario antes de escala. Mientras tanto, una instancia Docker por cliente (limitado pero viable para 10-20 clientes). |
| **Sin observabilidad** | 🟡 Medio | Fase 1: dashboard básico + alertas. Suficiente para 20-30 clientes. |
| **Competencia (Tango, Siare, sistemas grandes)** | 🟡 Medio | No compiten directamente (ninguno automatiza el ciclo completo). El riesgo es que agreguen features similares. Diferenciación: velocidad + simplicidad + AI-powered. |
